4. HOW EACH ITEM IS WORKED
================================================================================

One item per patch. The sequence, every time:

  1. CHECK THE BASE, BOTH WAYS. `git fetch`, confirm the PREVIOUS patch
     actually landed on the remote, and that the remote has not moved
     ahead. Rule 19 covers the second; the first was added on
     2026-09-24 after patch 414 sat unpushed for a turn while I built
     415 on a premise I had not checked.
  2. REPRODUCE THE FINDING against current code. If it does not
     reproduce, that is a result -- record it as such (004-6, A7) with
     what was tried, rather than quietly closing it.
  3. FIX IT, with the reasoning in the code where the next reader will
     need it.
  4. TESTS that would have caught it.
  5. CONTROLS: break the fix deliberately, confirm the tests fail,
     restore, confirm they pass. A control that proves nothing is a
     finding about the tests -- write the missing case (this has
     happened eleven times so far and has been worth it every time).
  6. BOTH SUITES, and ./lint.sh.
  7. Update AUDIT_CHECKLIST.csv and UNIFIED_ROADMAP.md.
  8. Package as a patch with an apply script that verifies the
     checksum, verifies the base, runs the gates, and only then pushes.

THE STANDARD IS IN PRINCIPLES.md. Measure rather than assume; state
what was not checked; correct a wrong claim in public when one is found
(patch 402 did exactly that about my own earlier work).

ALSO OPEN, raised while fixing other things:

    CONCERN-1  SQLite reads an unknown double-quoted identifier as a
               STRING LITERAL, so a misspelled column would fill every
               row with its own name. Only the drift check one layer up
               prevents it, and neither layer says so.
    CONCERN-2  the two adapters are safe from SQL injection by
               DIFFERENT mechanisms (quoting; bound columns). A third
               would have to rediscover which.
    CONCERN-3  silver rewriting a served value means a user who opens a
               prefilled field and saves it writes the standardised
               form back to the SOURCE. S1 is fixed; the shape remains.
    NEW-3      the confirm-time reach check uses the proposer's record
               as captured at propose time, so it catches the OBJECT
               moving, not the PROPOSER's clearance being revoked.
