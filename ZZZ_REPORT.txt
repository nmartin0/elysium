GOLD PUBLICATION HISTORY IS NEVER RECORDED ON THE ARROW PATH

From:     agentloop (LLM 2)
For:      backend -- core/mirror/ is not mine, and this is not fixed
Found:    during the first real VM run of scripts/llm_bench.py
Status:   REPRODUCED locally, root cause identified, not fixed
================================================================


WHAT YOU SEE
------------

Every sync after the first prints, for every object type:

    gold.Customer published, but its history was not recorded:
    'NoneType' object is not iterable
    published gold.Customer: 4 rows
    gold.Transaction published, but its history was not recorded:
    'NoneType' object is not iterable
    published gold.Transaction: 7 rows

The publication itself succeeds. Only the history fails, and it fails
into a warning rather than an error, which is why it has survived.


IT REPRODUCES ON THE SHIPPED DEPLOYMENT
---------------------------------------

    rm -rf /tmp/gh && mkdir -p /tmp/gh/data /tmp/gh/log
    # seed the dev fixtures into /tmp/gh/data, then:
    python3 -m scripts.run_sync     # first  -- clean
    python3 -m scripts.run_sync     # second -- both warnings appear

NOT ON THE FIRST SYNC, ONLY THE SECOND AND AFTER. That is why it is
easy to miss: a fresh checkout syncs once, looks clean, and the defect
appears the next time anyone runs it.


ROOT CAUSE
----------

    core/mirror/gold.py:369

        elif not isinstance(silver_rows, list):
            rows = None          # Arrow in, Arrow out: see below.

When silver arrives as an Arrow table rather than a list, `rows` is
set to None DELIBERATELY -- the data flows through as Arrow batches
instead, which is the point of that path.

But `rows` is then passed to `_record_history()` anyway, at both call
sites (gold.py:487 and gold.py:522), and reaches:

    core/mirror/gold_history.py:86
        changes = diff_snapshots(previous_rows, current_rows, id_field)

    core/mirror/changelog.py:125
        new = {str(row[id_column]): _as_strings(row) for row in current}
              TypeError: 'NoneType' object is not iterable

`record_publication()` guards `previous_rows is None` and returns 0.
It does not guard `current_rows`. On a FIRST publication the
previous_rows guard returns before reaching diff_snapshots, which is
exactly why the first sync looks clean.

Real traceback, obtained by unwrapping the except clause:

    File "core/mirror/gold_history.py", line 86, in record_publication
        changes = diff_snapshots(previous_rows, current_rows, id_field)
    File "core/mirror/changelog.py", line 125, in diff_snapshots
        new = {str(row[id_column]): _as_strings(row) for row in current}
    TypeError: 'NoneType' object is not iterable


WHY IT MATTERS MORE THAN THE WARNING SUGGESTS
---------------------------------------------

1. THE CHANGELOG IS EMPTY, NOT PARTIAL. `_record_history()` returns 0
   on this path, always. So `result.history_rows` is 0 on every
   publication, and the gold publication history records NOTHING for
   any deployment using the Arrow path -- which is the shipped dev
   deployment, since that is what reproduced it.

2. IT FAILS SOFT, BY DESIGN, AND THE DESIGN IS RIGHT. The docstring on
   `_record_history()` says it deliberately never raises into a
   publication: "Gold is published; failing to describe the change
   afterwards must not undo that". That is correct. It also means a
   total failure of the feature reads as a one-line warning between
   two success messages, and has done for however long.

3. IT TOUCHES G4. G4 is about readers pinning `current_snapshot()`
   rather than the `published-N` tag. A publication whose history was
   never recorded is precisely the state where "which snapshot was
   published, and what changed in it" stops being answerable after the
   fact. I am not claiming these are the same defect -- they are not
   -- but they compound.

4. THE SECOND-SYNC-ONLY BEHAVIOUR IS A TEST-SHAPE PROBLEM. Any test
   that syncs once cannot see this. That is the same lesson commit
   555868a already records about itself: "a fixture that is always
   absolute cannot see a bug that only exists when the path is
   relative". Here it is a fixture that always publishes once.


WHAT I DID NOT CHECK
--------------------

- Whether the Arrow path is the ONLY path in production, or whether
  some deployments take the list path and record history correctly. I
  only have the shipped dev deployment, and it takes the Arrow path.

- Whether `previous_rows` is also wrong on the Arrow path. It is
  populated (gold.py:458, `previous_rows = published_now`) and the
  failure is on `current_rows`, so it looks fine -- but I did not
  verify its CONTENTS are right, only that it is iterable.

- What the fix should be. There are at least two shapes -- materialise
  the Arrow batches for the diff, or record history from the Arrow
  side -- and they have different costs at scale. That is your call,
  in your file.

- Whether anything downstream reads the gold history and has been
  silently getting nothing.


ONE SUGGESTION, TAKE OR LEAVE
-----------------------------

Whatever the fix, the control worth running is a SECOND sync. The
first one passes today with the defect present, so a test that
publishes once cannot fail -- and a fix verified only against a first
publication would be verified against the one case that already
worked.
