An ontology between the model and your data

Ask your data questions. Without handing it over.

Elysium answers questions — and, with permission, makes changes — through an ontology you declare. The model never gets database access, and is never trusted to judge what it may see.

You declare the ontology. It is the whole interface.

Object types, fields, links and who may see what — written once, in YAML, and resolved live against your real databases at the moment a question is asked. 

# alice asks, and holds read:Customer.region
> which customers are in us-east?

  Ada Okafor      us-east
  Jun Park        us-east

# bob asks the same question, same instant
# his compartment is us-west
> which customers are in us-east?

  no customers match

# not "forbidden" — that would tell him

Same question. Same instant. Different answers.

Alice holds read:Customer.region. Bob does not, and his compartment is elsewhere. Neither of them configured this, and neither of them can tell the other's result exists.

The model was not consulted about any of it. It asked for named fields of named objects; the mediator decided what each caller could have.

A field this file does not declare does not exist, as far as any question is concerned. There is no schema introspection, no "SELECT *", and nothing for a model to discover on its own.

The model never sees a database

It asks for named fields of named objects. The mediator decides whether that caller may have them, then fetches. No SQL is generated, so none can be injected.

Reads are checked per field

read:Customer.email is a grant somebody holds or does not. Two colleagues asking the same question correctly get different answers.

Hidden is indistinguishable from absent

An object in a compartment you cannot see does not return "forbidden". It returns nothing — because "forbidden" tells you it exists.

A write is a proposal, not an action

When the model concludes something should change, the run stops and a person decides. The approver's own permissions are re-checked at the moment they approve — not the asker's, and not the ones anybody held when the proposal was made. 

PROPOSED  UpdateCustomerRegion
  customer   Ada Okafor
  region     us-west → us-east
  asked by   alice   # whose question caused it
  awaiting approval

APPROVED  by carol, 14:22:08Z
  re-checked carol's grants, re-evaluated the criteria,
  confirmed the proposal still applies
  written to primary_sql.customers

One organisation per instance

A server runs one organisation's data. There is no multi-tenant store to get wrong, and no row-level tenancy filter to forget.

Every access is logged

Each field read, each refusal and each approved write, tied to the request that caused it and the person who asked.

Your databases stay yours

Read adapters are structurally unable to write. Writing requires a separate, declared action type and a human decision.

See it working

The demo is a real Elysium instance with synthetic data. Ask it questions, propose a change, approve it as somebody else, and watch the audit log fill in.
