Trust centre

What Elysium does with your data, what it refuses to do, and what we have not yet proved to a third party.

Elysium is designed so that security is a property of the architecture rather than a policy. Everything below describes what the software enforces.

What the architecture enforces

Your data stays in your databases

Elysium reads from your silos and keeps a mirror inside your own deployment. Nothing is copied to us. There is no vector store, no embedding of your rows, and no model fine-tuned on your content.

Reads cannot write

The adapters that answer questions implement a read-only interface. Changing anything requires a separately declared action type and a human approval, on a different code path.

Permissions are per field

read:Customer.email is a grant somebody holds or does not, checked before the value is fetched rather than filtered from a result.

Mandatory access control underneath

An object in a compartment you cannot see returns nothing, not a refusal — because a refusal tells you the object exists.

One organisation per instance

A server runs one organisation's data. There is no shared store to misconfigure and no tenancy filter to forget.

Credentials are never in config

Connection settings carry references, not secrets. A plaintext password in a config file is rejected at load rather than warned about.

What is logged

Every field access, every refusal, and every approved write, tied to the request that caused it and the person who asked. The log lives in your deployment and is yours; we never see it.

Where your data goes

Nowhere. Elysium runs on infrastructure you control and reads databases you control. There is no Elysium-operated service in the path of a question, and so there is no subprocessor list for your data — if that changes, this page will say so before it does, with a dated changelog.

The exception is the language model. If you point a deployment at a hosted model, prompts leave your network to that provider. A deployment configured against a local model sends nothing anywhere. Which one you run is your choice, declared in your own config.

Certifications and documentation

Our compliance programme is developing alongside the product. Current security documentation, architecture detail and audit status are available to prospective customers on request, under NDA where appropriate.

For specific requirements — a data processing agreement, data residency commitments, or a security questionnaire — get in touch and we will respond with what applies to your deployment.

Reporting a vulnerability

Security reports are welcome and will be acknowledged. See security.txt for where to send them.
