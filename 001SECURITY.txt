2. THE WORK, IN ORDER
================================================================================

Nineteen open items. Severity is the audit's own. Every one came from

-------------------------------------------------------------------------------
-
2.1 Security, first
-------------------------------------------------------------------------------
-

E-02  UNAUTHENTICATED DISK EXHAUSTION. Ten requests took credentials.db
      from 100 KB to 16.3 MB by filling `login_attempts`. No login
      required. Start here: it is remotely triggerable by anyone who
      can reach the login endpoint.

E-01  VALIDATION ERRORS REFLECT REQUEST BODIES, secrets included. No
      `RequestValidationError` handler exists, so FastAPI's default
      echoes what was sent. A password in a malformed login body comes
      back in the error.

E-04  CSRF TOKEN COMPARED WITH `!=` rather than `compare_digest`. A
      timing side channel on a token comparison. The login path
      already does this correctly -- an earlier review measured it at
      0.7% delta over 25 samples -- so this is an inconsistency as
      much as a defect.

E-05  NO PERMISSIONS-POLICY HEADER. The other security headers ship;
      this one is missing.

-------------------------------------------------------------------------------
-
2.2 The write path
-------------------------------------------------------------------------------
-

F-27  CRASH RECOVERY LOSES DELETES, reports success, and writes a
      FABRICATED `create` into the write log. Reported as reproduced.
      The write log is the system of record for what was written; an
      invented entry in it is worse than a missing one.

F-25  GENERATION NUMBERS REPEAT AFTER RESTART and are consumed by
      REJECTED loads, so audit entries are attributed to the wrong
      configuration. Touches `core/deployment_loader.py`, which the
      backend agent owns -- coordinate before starting.

004-8 THE DOCUMENTED SINGLE ENFORCEMENT POINT IS NOT SINGLE:
      `WriteMediator` calls `_security_allowed()` directly rather than
      going through `check_access()`. Documentation and code disagree
      about where authorisation happens.

F-08  `submission_criteria`'s parameter-skip is safe only via an
      unstated precondition. Write the precondition down, or enforce
      it.

R50   A FEEDBACK-LOOP GUARD ON THE WRITE PATH: stop a value the
      system itself produced being written back as though a user
      supplied it.

-------------------------------------------------------------------------------

2.3 Audit and policy
-------------------------------------------------------------------------------
-

F-33  TWO CRITICAL AUTH CONTROLS ARE EACH DEFENDED BY EXACTLY ONE
      TEST. Found by mutation testing. One test is one accident away
      from a silent hole -- and the two controls are the ones that
      matter most.

F-21  `entries_for_request()` uses `readlines()`, loading the WHOLE
      audit log into memory and defeating its own `max_scan`.

F-13  `get_object()` audit entries carry no `request_id`, so the
      PREFERRED read path is absent from request traces.

F-05  THE RATE-LIMIT CHECK AND INCREMENT ARE SEPARATE TRANSACTIONS.
      Classic check-then-act: concurrent requests can both pass.

F-12a `THE SEVEN REAL GRANT PATTERNS` enumerates six and omits
      `manage:deployment`.

F-12b `login_attempt_tracker` claims a structurally read-only
      connection. It is not read-only.

================================================================================
4. HOW EACH ITEM IS WORKED
================================================================================

See 000COORDINATION.md §"How work is done". In short: check the base
both ways, REPRODUCE the finding, fix it with the reasoning in the
code, write the test that would have caught it, RUN A CONTROL (break
the fix, confirm the test fails, restore, confirm it passes), run
`./lint.sh` and both pytest tiers, then report in `STATUS_security.md`.

A control that proves nothing is a finding about your tests, not a
formality. That has happened eleven times on the backend branch so far
and has been worth it every time.
